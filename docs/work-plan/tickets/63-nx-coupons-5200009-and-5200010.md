# 63 - The two v84 NX coupons charge a meso and credit nothing

**Class:** v84 parity
**Work rows:** R16 - `docs/work-plan/V84-WORK-ROWS.tsv`
**Blocked by:** None - can start immediately

Two whole items v84 added carry a `maplepoint` value and nothing reads it. They are not unhandled:
they fall into an existing branch that treats every `520xxxx` item as a meso sack, and that branch
does something slightly worse than nothing. The fix is a data-driven read inside a branch that
already exists.

## R16 - `info/maplepoint` is never read

| item | node | value |
|---|---|---|
| **5200009** | `info/maplepoint` | **1000000** |
| **5200010** | `info/maplepoint` | **10000** |

Both verified in `wz/Item.wz/Cash/0520.img.xml`. Both are v84-new whole items -
`add-list/Item.txt:95` and `:96` - so neither has any v83 behaviour to preserve.

### The handler already exists and already fires

There are zero references to either **id** in `src/main/java` or `scripts/`, but that is because the
dispatch is keyed on **item type**, not on id:

```java
// UseCashItemHandler.java:428-431
} else if (itemType == 520) {
    player.gainMeso(ii.getMeso(itemId), true, false, true);
    remove(c, position, itemId);
    c.sendPacket(PacketCreator.enableActions());
```

`itemType` is `itemId / 10000` (`:102`), so 5200009 and 5200010 both land here today.

**The symptom is not "credits zero".** `ItemInformationProvider.getMeso:393-409` returns **-1** when
the item has no `info/meso` node:

```java
Data pData = item.getChildByPath("info/meso");
if (pData == null) {
    return -1;
}
```

Neither coupon has an `info/meso` leaf - only `05200000`, `05200001` and `05200002` do, the three
real meso sacks. So using either coupon calls `gainMeso(-1, ...)`, **charges the player one meso**,
consumes the item and credits nothing. That is the live behaviour to fix.

### The trap

`getEquipStats` only harvests `inc*`-prefixed nodes (`ItemInformationProvider.java:563-564`:
`if (data.getName().startsWith("inc"))`). `maplepoint` does not start with `inc`, so it will never
appear in a stat map no matter which stat path is used. It needs a direct `DataTool.getInt` read off
the item's `info` node.

## Precedent

Item-driven cash credit already exists at `Character.java:2084-2087`: `ItemId.isNxCard` ->
`getCashShop().gainCash(1, nxGain)`. That is the shape to copy - identify the item, read its value,
call `gainCash`. Note it is a ground-**pickup** path, not an inventory-**use** path, so it is the
call shape and not the call site.

The currency argument is the part to get right. `gainCash(1, ...)` is NX credit; the currency-2
precedent is `CouponCodeHandler.java:220`, `cs.gainCash(2, quantity);    //maplePoint`.
`maplepoint` is Maple Points, so the credit must go to the Maple Point currency and not to NX cash -
the node name is the evidence and `CouponCodeHandler` is the call shape.

## Acceptance criteria

- [ ] The fix lives in the existing `itemType == 520` branch at `UseCashItemHandler.java:428-431`.
      No new id-keyed branch is added.
- [ ] The branch reads `info/maplepoint` via `DataTool.getInt` and, when present, credits it to the
      **Maple Point** currency (`gainCash(2, ...)`); when absent it falls through to the existing
      meso behaviour unchanged.
- [ ] Using **5200009** credits **1000000** Maple Points and **5200010** credits **10000**, asserted
      by a test that stubs the cash shop and reads back both the credited amount **and the currency
      argument**.
- [ ] The amount comes from the WZ read, not from a literal in Java: changing the leaf changes the
      credited amount.
- [ ] **`gainMeso` is not called with -1 for either coupon.** A test asserts the player's meso is
      unchanged across the use - this is the live defect and it must be pinned.
- [ ] Items **5200000**, **5200001** and **5200002** still grant their `info/meso` amounts
      (1000000 / 5000000 / 10000000) and are unaffected by the change.
- [ ] The item is consumed exactly once per credit - no double-credit on a stacked use.
- [ ] An item with neither `info/maplepoint` nor `info/meso` routed through the same branch credits
      nothing, charges nothing, and does not throw.

Run the new test class with `-Dtest=<Name>`. **Do not run maven while sibling agents are active** -
they collide on `target/`.

## Do not

- Do not add an id-keyed branch for 5200009 / 5200010. The dispatch is type-keyed and a data-driven
  read covers both ids and any future sibling. A `grep` for the raw ids returning a hit is **not** a
  success criterion - it is the wrong design.
- Do not route `maplepoint` through `getEquipStats`. It only harvests `inc*`-prefixed nodes and will
  silently return nothing.
- Do not credit NX cash (`gainCash(1, ...)`) for a `maplepoint` node. The node names the currency.
- Do not leave `getMeso`'s -1 reaching `gainMeso`. Guard it, or the meso charge survives the fix.
- Do not fold ticket 64 (items 5550000 / 5550001, the timed cash slot expansion) into this one. It
  shares nothing with these two beyond being a cash item.
