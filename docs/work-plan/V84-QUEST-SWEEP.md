# v84-added quest completability sweep

Generated by `tools/playthrough/questsweep.py` (that file's docstring lists the five SELECT-only
DB dumps it needs). Output: `docs/work-plan/V84-QUEST-SWEEP.tsv`, one row per finding.

Regenerate:

```
python tools/playthrough/questsweep.py <scratchdir-with-the-five-dumps>
```

## How "v84-added" is defined

The set is **the repo's own enumeration**, not a re-derivation:
`docs/wz-baseline/merge-lists/09/Quest.paths.txt` (63 non-Evan ids) plus
`docs/wz-baseline/merge-lists/33/Quest.paths.txt` (135 Evan ids) = **198 quest ids**, which is the
count both tickets state and 63 + 135 closes exactly.

**Quests that existed in v83 and only had fields changed by v84 are OUT of scope**, on the same
authority: `docs/wz-baseline/add-list/Quest.txt` lists whole-node copy roots at depth 3
(`Quest.wz/Check.img/22529`) and field-level changes at depth 4-5
(`Quest.wz/Check.img/2208/0/end`). 795 paths are depth 3, **128 are depth 4-5**. Those 128 are the
"v84 changed an existing quest" side of the line and were not swept - they are pre-existing quests
the owner has already played.

## The five checks, and how completely each ran

All five ran over all 198. None was sampled.

| # | check | how |
|---|---|---|
| 1 | every required item has a source | `Check.img/<id>/{0,1}/item` plus every **negative** `Act.img` item (the hand-in), against `drop_data`, `drop_data_global`, `reactordrops`, `shopitems`, `makercreatedata`, any quest's positive `Act.img` grant, and any `gainItem(<literal>)` in `scripts/` |
| 2 | every required mob is placed | `Check.img/<id>/{0,1}/mob` against every map's `life` array, **plus** script spawners (`spawnMonster*`, `LifeFactory.getMonster`) **plus** `Mob.wz info/revive` chains |
| 3 | script-driven quests have a script | `startscript`/`endscript` in `Check.img` against `scripts/quest/<id>.js`, excluding the 39 medal quests that route to `scripts/quest/medalQuest.js` (ticket 44) |
| 4 | strings resolve | `QuestInfo.img/<id>/{name,0,1,2}`. There is **no** `String.wz/Quest.img` in this tree - quest text lives in `Quest.wz/QuestInfo.img`, as ticket 09 records |
| 5 | prerequisite chain intact | every `Check.img/<id>/{0,1}/quest/<i>/id` must itself have a `QuestInfo` node |

A sixth check was added because it is the failure mode that actually blocks this chain: **quest
records with no writer** (`infoNumber` with no `setQuestProgress` anywhere in `scripts/` or
`src/main/java/`). `Quest.canStart` and `canComplete` both run `canQuestByInfoProgress`, and
`autoStart` does not bypass it.

### Known limits of the sweep - stated, not hidden

- A drop source counts if its dropper is placed on **any** map. It does not ask whether that map has
  an inbound portal. The Slumbering Dragon Island rooms (`914100020`-`23`) are the known case where
  that matters; they are tracked separately in `V84-OPEN-ITEMS.md`.
- A `questreward` source counts without checking that the granting quest is itself completable.
- `gainItem` detection only sees numeric literals, not ids held in variables.
- Shop sources require the shop's NPC to be placed, but not that the NPC's shop is reachable.
- Check 4 asserts the strings exist. It does not proofread them.

| `ids` | the specific item / mob / npc / record id |

## Result

**Zero mechanical fixes.** Not one live v84-added quest is blocked by a missing item source; every
`MISSING_ITEM_SOURCE` row in the file sits behind an expired `end` date or in the Korean 1049x event
block. Nothing here needs a new `drop_data` row.

The live blockers were all placement or writer questions:

| rows | what | quests | outcome |
|---|---|---|---|
| 2 P0 | quest record 22598 has no writer | 22556, 22557 | **FIXED** - `scripts/portal/evanDollGR.js` |
| 4 P1 | quest records 22599 / 22600 / 22601 / 22604 have no writer | 22580, 22589 (x2), 22591 | **FIXED** - `onSDI.js`, `stopIceWall.js`, `outSDI.js`, `blackSDI.js`, `outAfrienMemory.js` |
| 4 P1 | npc 1013202 placed on no map - **and on none in pristine v84 either** | 22575, 22576, 22577, 22581 | **NOT A DEFECT** - see below |
| 1 P1 | PlayerNPC 9901000 has no `playernpcs` row | 22402 | **NOT A DEFECT** - the table has 6 rows, seeded by changeSet 163 |
| 1 P1 | mob 9300393 "Gentleman" placed on no map, in either tree | 22596 | **FIXED** - `scripts/map/onUserEnter/enterBlackfrog.js` |

**Not one of the twelve turned out to need an owner decision.** Every one was settled by reading the
quest's own `QuestInfo` / `Say` / `Check` / `Act` text against the hook list of the maps that text
names. The general method, which the next sweep should use before escalating anything:

1. `QuestInfo.img/<id>/showLayerTag`, then `WzPeek scan Map.wz tags <tag>`, finds the exact map
   OBJECT the client highlights during that quest - and its x/y usually lands on a portal. That is
   how 22598 was pinned: a `guide/tutorial/key` "press UP" sprite 5px from `evanDollGR`.
2. Then the **exhaustiveness argument**. Grep `add-list/Map.txt` for the map ids and list every
   `portal/N/script` and `info/onUserEnter`/`onFirstUserEnter` v84 declares. An `onUserEnter` whose
   value is the EMPTY STRING is v84 positively saying "no script here", not a missing node. If the
   whole area declares one hook and one record must be written, that hook is the writer.
3. One record slot carrying two values is one hook hit twice (22598, 22599). Two slots on one quest
   is two distinct triggers (22589 uses 22600 and 22604).

44 P2 rows are `NON_DEFECT`: 43 of them are npc **1013000 Mir**, who is the summoned dragon and not
a map NPC (`QuestActionHandler.java:52,91`), and one is mob **9101004**, a virtual kill counter
(`Character.java:7471`). Neither is placed in pristine v84 either. Do not "fix" them.

42 P2 rows are `DO_NOT_FIX`: 48 of the 198 quests carry an expired `end` date - the 2009 Evan launch
event, the Dragon Rider 375x line, the Korean winter event - and `EndDateRequirement` refuses them
before anything else is consulted. Ticket 44 established that precedent for quests 1048-1054.

### Four false positives the sweep had to learn about - do not re-file them

- **npc 1013202 "Black Shadow"** (22575, 22576, 22577, 22581) is not a placement gap. He is Hiver in
  disguise, and v84 unmasks him in the quest text: `QuestInfo.img/22581/2` reads *"#p1013202#'s name
  is #p1013203#"*, and 1013203 Hiver IS placed, on 922030000, where 22581 completes. Pristine
  `Say.img/22576/0/0` - *"Oh, you don't need to come all the way to see me in person, though"* - and
  `Say.img/22581/1/0` - *"I think this is our first meeting face to face"* - say outright that he is
  never physically present. `Etc.wz/NpcLocation.img/1013202/0` is `-1`, byte-identical to Mir's
  marker, and v84 ADDED that node. All four quests are `autoStart`, and `QuestActionHandler`'s whole
  proximity block sits inside a `!isAutoStart() && !isAutoComplete()` guard, so unlike Mir this one
  needs no special case at all. Pinned by
  `EvanChainRealLoad.blackShadowIsSpawnedOnNoMapAndNeedsNoSpecialCaseBecauseHisQuestsAreAutoStart`.
- **PlayerNPC 9901000** (22402) - the "`playernpcs` has 0 rows" premise was stale. It has 6, and row
  12 is `scriptid=9901000, map=102000004`, seeded by changeSet **163** and re-anchored onto v84
  footholds by **165**, both EXECUTED. A row genuinely is required (`QuestActionHandler` falls
  through `getNPCById` to `MapleMap.getPlayerNPCByScriptId`, and `null` is a hard refusal), and it is
  there. Query the table before filing this again.
- **4032474 "Seruf Pearl"** (22404, 22405) looks unsourced: its two `drop_data` rows sit on mobs
  4220000 and 9303014 and neither is in any map's `life`. It is fine. `scripts/event/AreaBossSeruf.js`
  spawns 4220001 into 230020100 at boot and `Mob.wz/4220001/info/revive` turns it into 4220000 on
  death. `EvanPorkSourceRealLoad#theSerufPearlIsAlreadyReachableViaTheAreaBossReviveChain` pins it.
  The sweep now follows script spawners and revive chains for exactly this reason.
- **Map `life` field order is not stable.** Kerning City writes `id` before `type`, Deep Valley
  writes `type` before `id`. A regex that assumes adjacency reports Kerning City as empty and files
  four imaginary "NPC not placed" blockers for the Kerning City investigation line (22534-22554).
  Those quests are fine; 1052000, 1052002, 1052103 and 1052106 are all on 103000000.

## The quest that started this: 22529 "Helping Beginner Adventurer Christopher"

Reported as *"killing Stumps, the sap never drops"*. **There is no defect.** The row exists and is
applied (`drop_data` id 23018, `(130100, 4032460, 1, 1, 22529, 80000)`, changeSet 156). Pristine v84
`QuestInfo.img/22529/1` names the dropper outright - *"dropped by the #o0130100#s"* - which is mob
**130100 "Stump"**, and our tree carries that string verbatim.

The three maps the quest sends you to are `106000000` / `106000100` / `106000200`, Deep Valley I/II/III.
They carry **Axe Stump 1130100**, **Ghost Stump 1140100** and **Dark Axe Stump 2130100** - and
pristine v84's `Map.wz` agrees exactly (Deep Valley I = 32x 1130100 + 10x 1140100 + npc 1022106).
Plain Stump 130100 is not in any of them, in either tree.

Plain Stump is one map away from Perion, where the chain already is: `101030000` East Domain of
Perion x26, `101040000` Perion Street Corner x32, `102010000` West Street Corner of Perion x22,
`100050000` Field South of Ellinia x31.

Adding a row on 1130100 or 1140100 would be inventing content v84 does not have, so it was not done.
If the owner wants the sap to drop where the quest sends him, that is a deliberate deviation and his
call to make.

One real inconsistency, cosmetic, not fixed: `Check.img/22529/1` asks for **2** after the halving,
while `QuestInfo`'s objective line still reads `#c4032460# / 3` and the v84 client's own unhalved
`Check.img` also wants 3. The player collects 3 and both sides are satisfied.
