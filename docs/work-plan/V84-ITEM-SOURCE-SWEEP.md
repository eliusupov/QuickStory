# v84-added item source sweep

Generated by `tools/playthrough/itemsweep.py` (that file's docstring lists the eight SELECT-only DB
dumps it needs). Output: `docs/work-plan/V84-ITEM-SOURCE-SWEEP.tsv`, one row per v84-new item that
nothing in this server can produce.

Regenerate:

```
python tools/playthrough/itemsweep.py <scratchdir-with-the-eight-dumps>
```

This replaces the unverified tracker line *"279 of 332 new v84 items have no source of any kind"*
(`V84-OPEN-ITEMS.md:105`). The script behind that figure is not in the repo and the figure does not
reproduce. **Neither number is right**: see *Correcting the tracker*, below.

## How "v84-added" is defined

From the authority, not from prose: `docs/wz-baseline/add-list/`, the computed v84-minus-v83 diff.
Every line there is a **copy root** - no listed path is an ancestor of another - so the depth of a
line tells you whether v84 added a whole node or only changed a field on a node v83 already had.
That is the same line the quest sweep drew.

| source | roots | what they are |
|---|---|---|
| `add-list/Item.txt` depth 4 | 234 | `Item.wz/<cat>/<img>.img/<itemid>` - whole-new item nodes. 164 Consume, 30 Etc, 21 Cash, 11 Special, 8 Install |
| `add-list/Item.txt` depth 3 | 2 | `Item.wz/Cash/0562.img` (a whole new image; its ids are enumerated from the image itself: **05620006, 05620007, 05620008**) and `Item.wz/Pet/5000067.img` (one new pet) |
| `add-list/Character.txt` depth 3 | 176 | `Character.wz/<slot>/<itemid>.img` - whole-new equip images. **20 of those 176 are `Character.wz/00002000.img/<effect>`**, which is an animation node on an image that already existed, not an item. Excluded -> **156 equips** |

**234 + 3 + 1 + 156 = 394 v84-new items.** Both add-list enumerations were re-counted rather than
taken on trust; the depth histograms are reproduced by the script and it aborts on a duplicate id.

Depth-5 and depth-6 paths in both files are field changes to nodes v83 already had
(`Character.wz/Cap/01002728.img/info/notExtend`, `Item.wz/Install/0301.img/03010069/effect2`) and
are **out of scope**, on the same authority the quest sweep used for the 128 depth-4/5 quest paths.

### Judgement calls, stated rather than buried

* **Hair (48 ids: 000319xx / 00033xxx / 00034xxx) is its own bucket, not an unsourced item.** A hair
  id is applied by a beauty-salon NPC that reads `Character.wz` directly and passes the raw id to
  `setHair`; it never becomes an inventory item, so **no drop, shop, quest or reactor row can ever
  exist for one** and calling it "unsourced" is a category error. They are emitted with verdict
  `COSMETIC_NOT_APPLICABLE` so the set stays complete and auditable. Corroboration that they are
  live content: 5 of the 48 (31990, 33030, 33050, 33150, 34060 - the Evan hairs) appear by literal
  id in `scripts/npc/1012103.js`, the stylist on 100000104.
* **Face: there is no Face bucket, because v84 added no Face image.** `add-list/Character.txt`
  contains zero `Character.wz/Face/...` paths at any depth. The bucket is kept in the script for the
  next diff, unused today.
* **Mounts (8 ids `Character.wz/TamingMob/019320xx`) are swept, in their own `mount` bucket.**
  Ticket 05 owns *making mounts work*; this sweep only answers *can the item be obtained*, and the
  answer is no for all 8. They are not loot: v84 grants a mount through the coupon item's
  `spec/script` (`consume_2430073` and friends) and none of those script files exists. The fix is a
  script, not a drop row - which is exactly why they belong in a bucket of their own instead of in
  the actionable drop-row list.
* **PetEquip (1 id, 01802064) is swept in its own bucket** and is `SOURCED`.
* `Item.wz/Special/0910.img` holds the 91xxxxx **cash-package** ids, not wearable content, so its 11
  ids are bucketed `cash`.

## The checks, and how completely each ran

All ran over all 394. Nothing was sampled.

| # | source checked | how |
|---|---|---|
| 1 | `drop_data` | dropper must also be **placed**: every map's `life` array, plus script spawners (`spawnMonster*`, `LifeFactory.getMonster`), plus `Mob.wz info/revive` chains |
| 2 | `drop_data_global` | membership |
| 3 | `reactordrops` | reactor must appear in some map's `reactor` array |
| 4 | `shopitems` join `shops` | the shop's NPC must be placed |
| 5 | `makercreatedata`, `makerrecipedata`, `makerrewarddata` | membership. Cross-checked against `Etc.wz/ItemMake.img`: **zero** overlap with the unsourced set, so no Maker recipe is missing a DB row |
| 6 | quest grants | every **positive** item in `Quest.wz/Act.img` |
| 7 | scripts | `gainItem(<numeric literal>)` in `scripts/` and `src/main/java/` |
| 8 | scripts, weaker | a bare numeric mention of the id in a `.js` - see *script mentions* below |
| 9 | cash shop | `Etc.wz/Commodity.img` (what `CashShop.CashItemFactory.loadAllCashItems` reads), with SN and OnSale, plus `Etc.wz/CashPackage.img` |
| 10 | containers | any `Item.wz` node carrying `reward/<n>/item`, which is what `ItemInformationProvider.getItemReward` consumes. Two images have them: `Consume/0202.img` (66 containers) and `Cash/0553.img` (17) |
| 11 | `monstercarddata` | membership |

The placement reader is **lifted from `tools/playthrough/questsweep.py`**, not reinvented, so both
of the traps that file documents are handled the same way here. Both were re-asserted against this
tree before the sweep was trusted:

* **Map `life` field order is not stable.** Kerning City writes `id` before `type`, Deep Valley
  writes `type` before `id`. Each entry is read as a block and both fields pulled by name. Verified:
  npcs 1052000 / 1052002 / 1052103 / 1052106 are all found on 103000000, and mobs 1130100 / 1140100
  on 106000000. A regex assuming adjacency reports one of those two maps as empty. 3064 maps carry a
  `life` array, 787 distinct mobs and 1231 distinct npcs.
* **Script spawners and revive chains count as placement.** `AreaBossSeruf.js` spawns 4220001 into
  230020100 and `Mob.wz/4220001/info/revive` turns it into 4220000 on death; ignoring either reports
  a live item as unobtainable.

`tm=999999999` portals are the third documented trap. It does not apply here - nothing in this sweep
reasons about reachability between maps, only about whether a granter is placed at all.

### One check the quest sweep did not have: expired granters

A quest whose `Check.img/<id>/0/end` is in the past is refused by `EndDateRequirement` before
anything else is consulted, so it can neither grant nor consume anything. This sweep therefore does
**not** count a `questreward` whose every granting quest is expired; it records it in
`sources_found` as `questreward(... - all expired)` and the item counts as unsourced. That moved 26
items out of `SOURCED`. The quest sweep's stated limit - *"a `questreward` source counts without
checking that the granting quest is itself completable"* - is closed for the end-date case, and only
for that case.

The same date is applied to consumers: a `REQUIRED BY LIVE QUEST` note in the TSV means the quest
carries **no** expired end date, and is the only kind of note that can represent a live blocker.

### Script mentions - the weakest evidence in this file, and why it is here

`gainItem` detection only sees numeric literals. `scripts/npc/9000011.js` keeps its entire prize
table in `Array()` literals and gains by index; `scripts/quest/28362.js` picks between two ids on
gender and calls `qm.gainItem(gift, 1)`. Both are real grants that a literal-only scan misses, and
missing them is how a working item lands on an "unobtainable" list.

So a bare numeric mention of the id in a `.js` is recorded as a source, labelled `script_mention`,
and for `scripts/npc/<n>.js` it is only counted live if npc `<n>` is actually placed. **12 items are
sourced by nothing stronger than a mention.** All 12 were read by hand and all 12 are real:

| ids | file | grant |
|---|---|---|
| 1050168, 1051209 Evan Outfit (M/F) | `scripts/quest/28362.js:13,19` | `var gift = ...getGender() == 0 ? 1050168 : 1051209; qm.gainItem(gift, 1)` |
| 2430036-40 (1-day mount coupons), 2430073-77 (15-day) | `scripts/npc/9000011.js:1-10` | `prize1`/`prize6` arrays, npc placed on 200000000 |

This also settles a loose end in `V84-OPEN-ITEMS.md:106` - the *"5 mount coupons that ARE
obtainable"* are 2430073-77 and this is where they come from.

### Known limits - stated, not hidden

* **A drop source counts if its dropper is placed on *any* map.** It does not ask whether that map
  has an inbound portal. Same limit the quest sweep carries.
* **A shop source counts if the shop's NPC is placed.** It does not ask whether the NPC's shop is
  reachable, or whether the player can afford it.
* **`gainItem` detection sees literals; everything else is a mention, not a proof.** A mention can
  in principle be a coincidence (an id that happens to equal a map or mob id in the same file). All
  12 mention-only items were checked by hand this round; a future run must re-check any new ones.
* **`Etc.wz/Commodity.img` in this tree is not pristine v84.** `V84-OPEN-ITEMS.md` records SNs
  60001000-60001005 as local additions absent from v84 and a Commodity divergence against real v84
  on shared SNs. A `CASH_ONLY` verdict is therefore *this server's* cash shop, not a claim about
  what Nexon sold.
* **No drop rate, dropper or coordinate was invented anywhere in this file.** Where the data does
  not settle a value the answer is UNKNOWN and the row says so. `SOURCES.md` Tier 1 is explicit that
  drop tables were never shipped in any carve; nothing here can recover one.
* **The sweep does not ask whether an item is *useful*.** `2430073` has a `spec/script` pointing at
  a `consume_2430073` file that does not exist; the sweep still calls the coupon sourced, because it
  is. Broken-on-use is a different defect class, already tracked at `V84-OPEN-ITEMS.md:106`.
* **Container chains are followed one level.** If a container is itself only inside another
  container, the inner item is reported `CONTAINER_ONLY` against the direct parent. No such chain
  exists in the current data.

## Columns

| column | meaning |
|---|---|
| `item_id` | the item |
| `item_name` | `String.wz` verbatim, including the 5 ids that are still Korean (1012161, 1142166, 4001395, 4032528, 4032529) and the 28 with no `String` entry at all (blank) |
| `category` | the equip slot (`Weapon`, `Cap`, ...) or the `Item.wz` category (`Consume`, `Etc`, `Install`, `Cash`, `Special`, `Pet`) |
| `add_list_path` | the exact `add-list` copy root the id came from - the audit trail back to the authority |
| `sources_found` | sources that **exist but are not reachable**. Blank means nothing at all references the item. 36 rows are non-blank |
| `bucket` | `equip_weapon`, `equip_armor`, `equip_accessory`, `consume`, `etc`, `install`, `cash`, `pet`, `mount`, `cosmetic_hair_face`, `pet_equip` |
| `verdict` | `PARITY_GAP` · `CASH_ONLY` · `CONTAINER_ONLY` · `NO_SOURCE_IN_V84` · `COSMETIC_NOT_APPLICABLE`. `SOURCED` rows are omitted and only counted |
| `note` | the evidence. `REQUIRED BY LIVE QUEST <ids>` is the only marker that can mean a live blocker |

Verdicts are assigned in this order, each from data:

1. `COSMETIC_NOT_APPLICABLE` - bucket is `cosmetic_hair_face`. Decided **before** any source lookup.
2. `SOURCED` - any live source above. Omitted from the TSV.
3. `CONTAINER_ONLY` - the item is inside a `reward` container and every such container is itself
   unsourced.
4. `CASH_ONLY` - a `Commodity.img` row exists with `OnSale=0`. All 15 are also inside a
   `CashPackage.img` package, which is independent corroboration that they are package content
   rather than orphans.
5. `NO_SOURCE_IN_V84` - either `info/cash=1` with **no** Commodity row at all (v84 ships the art and
   lists no way to buy it), or `only=1 + tradeBlock=1 + price=1` (GM/test item, handed out by
   command).
6. `PARITY_GAP` - everything else. **This is a triage queue, not a list of confirmed bugs**: it
   means *no source was found and no data-driven reason was found to expect none*.

## Correcting the tracker

`V84-OPEN-ITEMS.md:105` reads *"279 of 332 new v84 items have no source of any kind - no drop, shop,
quest, reactor, Maker or cash-shop row. Includes all 18 new endgame weapons (reachable only from
containers that are themselves unobtainable)."*

* **332 is wrong.** The add-list yields **394**. 332 does not fall out of any defensible reading of
  it: 394 minus the 48 hair ids is 346, minus the 8 mounts is 338, minus the 1 PetEquip is 337.
  Whatever set produced 332 is not recoverable, so the old figure is **unfalsifiable** rather than
  merely wrong - which is the reason this sweep exists.
* **279 is wrong.** 273 rows are written, and 48 of those are hair, which cannot have a source at
  all. The honest headline is **225 v84-new items that this server cannot produce**, of which
  **127** are the actionable `PARITY_GAP` queue.
* **"all 18 new endgame weapons" is refuted, on all three claims.** There is no 18-item set of
  v84-new weapons matching that description.
  * v84 adds **39** new weapon images.
  * **17**, not 18, are `Character.wz/Weapon/01302900.img` through `01302916.img`. They are **not
    endgame** - "One Shot Kill Sword", "Boss Kill Sword", "Slow Sword", reqLevel 10, incPAD 10,
    `only=1 tradeBlock=1 price=1`. They are GM test swords. And they are **in no container**:
    1302900 appears in exactly two files in the entire tree, its own `Character.wz` image and
    `String.wz/Eqp.img`. Verdict `NO_SOURCE_IN_V84`.
  * The most likely origin of the "18" is `013029xx` (17) counted together with `01302132` "Pig
    Herding Stick", the only other new one-handed sword. That is the sole 18-item weapon set in the
    diff, and it is not endgame and not container-gated either.
  * The claim's **mechanism** is real but describes a different, smaller set: **7** weapons are
    genuinely reachable only from containers that are themselves unsourced - 1332100 Nageling,
    1402073 Askaron, 1432066 Bellum Spear, 1442090 Machlear, 1462076 Inferna, 1482051 Crusio (all
    reqLevel 105) from the five **Dragon Rider's <job> Box** items 2022652-2022656, and 1382092
    Circle-Winded Staff (reqLevel 30) from cash coupon 5530027. An 8th equip, 1102231 **Sirius
    Cape**, sits in four of those same boxes.
  * The set that best fits the words *"new endgame weapons"* is the **6 "Neo" weapons**, reqLevel
    83-85, whose `String.wz` descriptions all read *"Only specifically designated scrolls can be
    used on it"*: 1372059 Neo Phoenix Wand, 1402074 Neo Heaven's Gate, 1442091 Neo Eclipse, 1452090
    Neo Dark Arund, 1472101 Neo Black Mamba, 1482052 Neo Steel Renault. They are **not** in any
    container - nothing in this tree references them at all. Verdict `PARITY_GAP`, and how GMS
    distributed them is **UNKNOWN**; it is not in the client data.
