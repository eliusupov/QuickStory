# WZ provenance — this fork vs P0nk/Cosmic upstream (ticket 02e)

Method: git, not binary diffing. Added remote `upstream = https://github.com/P0nk/Cosmic.git`
(fetch only, never pushed) and diffed the tracked `wz/` XML tree.

Reproduce:

```
git remote add upstream https://github.com/P0nk/Cosmic.git
git fetch upstream
git merge-base HEAD upstream/master
git diff --name-status <merge-base> HEAD -- wz/
```

## 2. Server-side WZ customization — per file

`wz/` holds 22,180 `.img.xml` nodes. Exactly **3 files** differ from upstream, in
**2 commits** (`a95a1914` 2025-10-03, `ab2c8d6f` 2025-09-22).

| WZ file | files added | files modified | files deleted | semantic node changes |
|---|---|---|---|---|
| Quest.wz | 0 | 2 (`Act.img.xml`, `Check.img.xml`) | 0 | 2,785 leaf values |
| String.wz | 0 | 1 (`Cash.img.xml`) | 0 | 6 leaf values |
| Base / Character / Effect / Etc / Item / Map / Mob / Morph / Npc / Reactor / Skill / Sound / TamingMob / UI | 0 | 0 | 0 | 0 |

The raw `git diff` on the two Quest files is ~14,000 lines, but that is almost
entirely a serializer reformat (`<imgdir name="0">\n</imgdir>` → `<imgdir name="0"/>`);
the file was regenerated by a different XML writer. Canonicalising both sides to a
path→value map (parse XML, flatten, compare) reduces it to the numbers above.

Character of the real change:

- **Quest.wz** — *every* changed leaf is a `count` field, across 670 quest ids in
  `Act.img` and 1,036 in `Check.img`. Zero added or removed nodes. This is a quest
  item-requirement / reward-quantity rebalance (values roughly halved: `-5→-3`,
  `-100→-50`, `-50→-25`).
- **String.wz/Cash.img** — 3 cash coupons (`5211048`, `5211060`, `5360042`), `name`
  and `desc` only, retimed to match shortened server durations (4h→40min, 2h→20min).
  Cosmetic text; pairs with the `CashShop.java` change in the same commit.

Full machine-readable list: every changed path is `wz/Quest.wz/{Act,Check}.img/<questId>/<n>/item/<i>/count`
or `wz/String.wz/Cash.img/<itemId>/{name,desc}`. Enumerate exactly with:

```
python - <<'EOF'
import subprocess, xml.etree.ElementTree as ET
def flat(rev, p):
    r = ET.fromstring(subprocess.check_output(['git','show',rev+':'+p])); o={}
    def w(n,pre):
        for c in n:
            q=pre+'/'+c.get('name','')
            o[q]='<dir>' if c.tag=='imgdir' else c.tag+'='+str(c.get('value'))
            if c.tag=='imgdir': w(c,q)
    w(r, r.get('name','')); return o
for p in ['wz/Quest.wz/Act.img.xml','wz/Quest.wz/Check.img.xml','wz/String.wz/Cash.img.xml']:
    a,b = flat('cf5ba092338b99f1a1010dab2c37681de5f9168f',p), flat('HEAD',p)
    for k in sorted(set(a)&set(b)):
        if a[k]!=b[k]: print(p, k, a[k], '->', b[k])
EOF
```

### Verdict on the approach

It works, and it is decisive: **the server `wz/` tree is upstream-identical apart from
a quest-cost rebalance and three coupon strings.** Not a large protect-list — because
there is essentially nothing server-side to protect. That is a useful negative.

## 3. Does this explain ticket 02's findings?

**Short answer: no — and it actively refutes the hypothesis, while confirming ticket 02
was right.**

### 3a. The Map.wz v84 finding — server customization cannot explain it, and doesn't

The reasoning in the dispatch holds. `docs/wz-baseline/map-v83-only-audit.txt` compares
two client dumps (stock v83 vs the v84 source) and touches neither `wz/` nor the live
client, so nothing in this repo could have caused it. Confirmed independently:

- All **832** genuinely-absent paths from that audit exist in this repo's
  `wz/Map.wz/` — which is byte-identical to P0nk/Cosmic upstream (checked by
  `os.path.exists('wz/' + path + '.xml')`, 832/832 hit, 0 miss).
- That includes the full Monster Carnival stage series (`970030100`–`970042717`,
  823 files under `wz/Map.wz/Map/Map9/`), Mu Lung Dojo (`925*`, 601 files) and
  Sheep Ranch / Happyville (`9105*`).
- Node counts line up: `wz/Map.wz` has 5,609 `.img` nodes; ticket 02's stock-v83
  reference reports 5,616 (the delta is non-`.img` container dirs). The v84 source
  reports 4,848.

So that content is real v83 content, present in an untouched upstream tree. Ticket 02's
conclusion — the v84 `Map.wz` source is damaged and not safe to import from — is
independently corroborated. Server customization explains none of it.

### 3b. Where customization *is* relevant — the protect-list is mislabelled

This is the part the owner's instinct was pointing at, but the custom content is
**upstream Cosmic's, not this fork's**. Cross-checking every entry of
`docs/wz-baseline/protect-list/` against the upstream-identical `wz/` tree:

Every single protect-list entry is content that P0nk/Cosmic upstream ships. None of it
originated in this fork. Concretely: `wz/Npc.wz` holds 5,603 ids with prefix `99`
(`9901xxx`, `99065xx`, `9977777`) against ~1,620 genuine v83 NPCs — the classic
HeavenMS/Cosmic injected-NPC block. Same story for `String.wz/Cash.img` later-version
cash items, `Etc.wz/DeveloperNpc.img`, quest `7778`, `Map/Map7/777777777.img`,
reactors `9400300`/`9400301`, faces `000208xx`/`000218xx`.

Practical impact on ticket 02:

- The protect-list is still **operationally correct** — that content must survive a
  client upgrade, whoever authored it.
- Its **framing is wrong**. Calling it "this server's custom content" implies a local,
  undocumented provenance. It is upstream Cosmic's, versioned in git, and can be
  regenerated from `upstream/master` at any time rather than salvaged from a live
  client binary. That makes it far cheaper to handle than the ticket assumes.

### 3c. The one assumption that is genuinely broken

Any step that treats `wz/` as **stock v83** is wrong. It is *Cosmic-flavoured v83*:
v83 plus roughly 5,300 injected NPCs, extra cash strings, extra reactors/faces/maps.
For "is this real v83 content?" questions, `wz/` gives false positives on that block.
It is reliable in the other direction — anything present in `wz/` and also in a stock
v83 client dump is unambiguously real v83.

## 4. Is `wz/` usable as a v83 baseline?

**Yes, for structure and values — no, for anything binary.** It is far more complete
than a typical server-only tree.

Contains:

- Full node hierarchy and every scalar leaf (`int`, `string`, `vector`, `float`,
  `short`, `uol`) for all 16 WZ files, 22,180 `.img` nodes.
- `Map.wz` carries the **client-side** node set, not just server fields:
  `info`, `foothold`, `portal`, `life`, `reactor`, `ladderRope`, `seat`, `ToolTip`,
  plus `back` / `obj` / `tile` layer references and `miniMap` metadata. The
  `Back/` (107), `Obj/` (107) and `Tile/` (102) resource trees are present too.
- `canvas` nodes are present **as metadata** — `width`, `height`, `origin`, `z` — so
  sprite dimensions and anchors are queryable.

Does not contain:

- Any pixel or audio payload. Zero `.png` anywhere in the tree; `canvas` elements have
  no data child, `Sound.wz` has 44 `.img` shells with no MP3.
- Consequently `du` is misleading as a completeness signal: 315 MB `Map.wz`,
  186 MB `Character.wz`, 1 MB `Sound.wz`.

Good for: node-path presence/absence checks, id enumeration, mob/npc/item/skill stat
lookups, map spawn/portal/foothold/reactor geometry, string tables, sprite
dimensions and origins, quest data. Everything is plain XML, so `grep`/`ElementTree`
replaces binary WZ tooling for all of it.

Not usable for: producing or repairing client-facing image or sound assets, and not a
substitute for a stock v83 dump when the question is specifically "did retail v83 have
this?" (see 3c).
