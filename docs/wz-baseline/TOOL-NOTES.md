# WZ diff tool — notes for tickets 04–09

Tool: `docs/wz-baseline/tool/` (C# console, MapleLib). Outputs in this directory were
regenerated by it on 2026-08-15 and are **final**, not provisional — `wz-data/v84/` was
confirmed byte-identical to a fresh carve of `GMSSetupv84.exe`.

## Running it

```
dotnet run -c Release --project docs/wz-baseline/tool -- <outRoot> [v83Dir] [v84Dir] [liveDir]
```

All four roots are positional args; the defaults are this machine's layout. A root may be
several `;`-separated directories, searched in order per file — that is how the v83
`Reactor.wz` baseline is picked up from `wz-data/v83-reactor/` without touching
`wz-data/v83-stock/`.

MapleLib lives outside the repo, so `WzDump.csproj` names it via an overridable property:
`dotnet build -p:MapleLibProject=<path>\MapleLib.csproj`.

Full 18-file × 3-tree sweep: ~5 minutes, ~55,000 images parsed.

### Merge-verification mode

There is no separate mode. To prove a merge changed nothing it should not have, run the tool
with the pre-merge tree as `v83Dir` and the post-merge tree as `v84Dir`, then read
`modified-list/*.txt` (images whose bytes moved) and `removed-list/*.txt` (nodes that
disappeared). `add-list` is then the set of nodes the merge introduced. Point `liveDir` at the
post-merge tree too, or at anything harmless.

## Outputs

| dir | meaning |
|---|---|
| `add-list/` | in v84, not in v83-stock. What the patch adds. |
| `removed-list/` | in v83-stock, not in v84. **v84 genuinely deletes content** (833 `Map.wz` roots). Never wholesale-swap a wz file. |
| `protect-list/` | in the live client, in neither stock tree. Ezorsia/custom content, must survive any merge. |
| `modified-list/<wz>.txt` | path exists in both stock trees, `WzImage.BlockSize` differs → v84 *edited* it. |
| `modified-list/<wz>.live.txt` | path exists in v83-stock and live, BlockSize differs → the live client edited it. Treat as custom. |

Every manifest carries a header. Add/remove/protect lists are **copy roots**: no listed path
is an ancestor of another, so copying a listed path already covers everything beneath it.
Do not re-copy children. (This is why counts differ from the first committed manifests — e.g.
`protect-list/Etc.txt` went 5267 → 4: those 5267 paths were all sub-keys of 4 custom images.)

`—` in `SUMMARY.md` means *not measurable* — a tree lacks that file. It never means zero.

## Defect codes in the source comments

`Program.cs` cites the code review that produced this rewrite. Legend:

| code | defect |
|---|---|
| H1 | `ParseImage()` failure silently read as "image has no children" |
| H2 | expand/no-expand allowlist inconsistent; `Map.wz` on the wrong side |
| H3 | no modified-node list, so additive-only merging is unverifiable |
| H4 | missing `Reactor.wz` baseline printed as `0` instead of "unknown" |
| H5 | live `.wz` files that were never baselined, invisibly |
| M1 | an exception aborted the encryption-version fallback loop |
| M3 | manifests listed parents and children, inviting double-copies |
| M7 | input roots and the MapleLib project reference hardcoded |

## Design decisions

**Every image is expanded one level, always.** The old per-file allowlist
(`String/Quest/Skill/Item/Etc/UI`) was a guess about which files hold "bucket" images, and it
put `Map.wz` on the wrong side. You cannot tell a bucket image from an entity image without
parsing it, so the rule is now structural in the only honest sense: parse everything, then
`UnparseImage()` immediately so memory stays flat across ~55k images. Cost is CPU (~5 min),
not RAM. There is no allowlist left to get wrong.

What that bought, all previously invisible: 5 new `Map.wz/Obj/*` sub-sets, `Map.wz/Effect.img/evan`,
`Map.wz/Map/Map2/220011001.img/miniMap`, and 6 `Character.wz/Afterimage/mace.img/*` entries.

**Parse failures are hard errors.** `WzImage.ParseImage()` reports failure by *returning false*,
not throwing (`WzImage.cs:466,473,481`), and the `WzProperties` getter throws that bool away and
hands back an empty, non-null collection. The old tool read the getter, so a failed image looked
exactly like an image with no children — silently. The tool now calls `ParseImage()` itself,
records failures, and `SUMMARY.md` always prints `<n> images parsed, <m> parse failures` so a
clean run is provable rather than assumed.

**Encryption-version fallback tries all three IVs.** A wrong IV throws `InvalidDataException`
from `WzFile.ParseWzFile`; that is a failed *candidate*, not a failed file. Relevant to ticket 03:
HaRepacker's default write path is BMS, so re-saved files will need the fallback.

## How far to trust `BlockSize`

It is a cheap change *detector*, not a content hash. It is neither sound nor complete:

- **False positives from repacking.** `Mob.wz` v83→v84 shows 1171 changed images, but 671 of
  them differ by ≤4 bytes — Nexon re-encoded the archive; the content is very likely identical.
  Read `modified-list` sizes, not just row counts.
- **False negatives are possible.** A replacement that happens to compress to the same length is
  invisible. Unlikely, not impossible.

Where it is worth trusting: `modified-list/Character.live.txt` has **5114** rows, none of them a
trivial ±4-byte delta. That is Ezorsia's 18.6 MB of HD art, sitting under paths that also exist
in stock v83 — content a presence-only diff cannot see at all (`protect-list/Character.txt` finds
only 4 nodes). **Ticket 04–09 rule: for `Character.wz`, treat every path in
`modified-list/Character.live.txt` as protected. Do not overwrite it with v84 data.**

Escalation if that is not good enough: hash the canonical serialization of each parsed image
(not its raw block bytes — those embed absolute offsets and change on any re-save). That means
fully parsing and re-serializing three trees; not done, deliberately, and not worth it unless a
specific merge dispute needs it.

## Known gaps

- **`Sound.wz/BgmGL.img` (live) fails to parse** — `InvalidDataException: WZ extended property
  exceeds its declared block`. The only parse failure in any tree. It is a pre-existing defect in
  the live client's `Sound.wz`, not something this tool introduced, but any BGM work must know
  that image's contents are unreadable by MapleLib.
- **`Base.wz`, `Effect.wz`, `Morph.wz`, `Sound.wz`, `TamingMob.wz`, `EzorsiaV2_UI.wz` have no
  stock baseline** — they exist only in the live tree, so every cell for them reads `—`. They are
  now *visible* as unmeasured rather than silently absent, but they are still unmeasured.
  **Ticket 05 (v84 mounts) needs `TamingMob.wz` from both stock trees and has no source data
  until someone extracts them** from `GMSSetupv83.exe` / `GMSSetupv84.exe`. New-area BGM needs
  `Sound.wz` the same way.
- **`List.wz` is not a WZ archive** (`WZ header FStart is outside the file` under all three IVs).
  Expected — it is a legacy flat list file. Row kept so the failure is visible.
- **Sub-property byte sizes are not tracked** — only whole-`.img` `BlockSize`. Add/protect byte
  totals read 0 for files whose deltas are all sub-node-level (String, Quest, parts of UI/Item/Etc).
